## 1. Establish the physical operating envelope

Measure actual straight-line acceleration, braking distance, maximum stable speed, yaw response, turning radius and slip on flat and sloped asphalt. Repeat at several speeds. Commands are target speed and yaw rate for a skid-steer vehicle; actual yaw can be much lower because four wheels scrub against the surface.

At the current 0.033 m wheel radius, 5 m/s requires about 1,447 wheel rpm. Do not assume the existing motors, friction and rigid tandem can achieve that stably. Near a 0.8 m radius corner, constant 5 m/s would require about 31 m/s² lateral acceleration. Use a measured curvature-dependent speed envelope; `sqrt(mu*g*radius)` is only an initial flat-road estimate. Account separately for slopes, skid-steer behavior and braking before corners.

The 360/5 = 72-second calculation is a geometric reference. If 5 m/s is the maximum, braking makes a centerline lap longer than 72 seconds. A learned racing line also has a different length. Optimize successful measured lap time rather than promise a specific time or global optimum.

Deliverable: calibrated speed/yaw limits, acceleration limits and a conservative speed profile indexed by track station.

## 2. Make a reproducible training interface

The existing UDP bridge is useful for interactive experiments but is wall-clock driven. Before training, add episode reset and synchronized stepping to the Unreal plugin:

- Include episode ID, command sequence, physics-step counter and simulation timestamp in every response. Reject old commands and mismatched observations.
- Advance an exact number of physics substeps per action. A candidate is 120 Hz physics and 20 Hz control; validate constraint stability and timing before adopting it.
- Reset every tandem rigid body's pose and linear/angular velocity, plus constraints, controller state, sensor buffers and progress counters. Resetting only the actor root is insufficient.
- Seed obstacle placement and randomization; acknowledge that Chaos runs may still have numerical nondeterminism.
- Return observations after the requested physics steps, with sensor ages and validity masks. Use simulation time for lap timing.

Wrap this in a Python Gymnasium environment: `reset(seed)` returns observation/info; `step(action)` returns observation, reward, terminated, truncated and info. Collision, rollover, out-of-track and completed lap are task termination conditions; a time limit is truncation. Follow the official [environment creation guide](https://gymnasium.farama.org/tutorials/gymnasium_basics/environment_creation/) and [environment API](https://gymnasium.farama.org/api/env/).

Important coordinate correction: the current bridge reports `x_m=(UE_X-10000)/100`, while this track uses origin `UE_X=15000`. Convert bridge coordinates to track coordinates using `track_x=bridge_x-50`, `track_y=bridge_y`, `track_z=bridge_z`. These pose values are simulator ground truth, not sensor-derived odometry.

Deliverable: reset/step smoke test with stationary stability, reproducible initial state and no stale packets.

## 3. Build a baseline and objective boundary checks

Start with a slow centerline follower using measured pose, a look-ahead controller and the calibrated speed profile. Complete a full lap before adding learning. Project onto a locally consistent track segment using previous progress and ordered sector gates; a global nearest-point lookup can jump between neighboring hairpins.

Check the complete four-wheel vehicle footprint against the drivable boundary polygon, with a margin. Checking only the vehicle center permits wheels to cut corners. Include the rigid front-to-back connection in collision and clearance checks. Define one lap as all ordered gates followed by a forward finish crossing. Track signed progress and reject shortcuts, reversing exploits and repeated finish crossings.

Deliverable: baseline lap time, trajectory, boundary margin and collision log. This establishes whether RL actually improves performance.

## 4. Train a map-assisted policy first

Initially provide privileged simulator pose and the known track map. This isolates driving optimization from localization errors. Suggested observations: lateral and heading error; speed and yaw rate; previous action; upcoming curvature, slope and boundary distances; both lidar scans with age/validity masks; and a short history of measurements. Normalize continuous observations and actions.

Use continuous normalized actions mapped to bounded target speed and yaw rate. Apply calibrated acceleration/yaw slew limits. Begin with a residual policy that adjusts the baseline commands within small limits, then widen those limits as successful laps become reliable. This gives the learner useful behavior from the first episode.

Start with SAC as a continuous-control candidate. PPO is a useful comparison if multiple independent Unreal instances are available. Choose based on measured sample efficiency and stability, not an assumed universal winner. The [Stable-Baselines3 RL tips](https://stable-baselines3.readthedocs.io/en/master/guide/rl_tips.html) cover normalization, evaluation and custom-environment pitfalls.

Reward signed forward progress and penalize elapsed simulation time, collisions, boundary violations and excessive command changes. Use ordered gates and progress bookkeeping to prevent farming the same segment. Avoid a strong centerline reward: the racing line should be free to use the permitted road width. Treat staying on track and avoiding obstacles as constraints assessed separately from reward. A high reward alone does not prove safe completion.

Curriculum: low-speed empty-track laps; varied start positions; progressively higher speed; static obstacles; varied obstacle arrangements; then moderate friction/mass/sensor/timing variations. Keep evaluation seeds separate from training. Use multiple training seeds and save both successful and failed trajectories.

## 5. Add perception without hiding its limitations

The existing two 2D lidars detect geometry. They cannot detect white paint on asphalt. Keep the boundary map plus localization, or implement a camera pipeline that estimates lane boundaries. The port now provides ideal lidar, front RGB images and chassis IMU measurements, as well as explicitly labeled ground-truth pose. See `simulation_ml/integrations/rapyuta/RGB_IMU.md`. Wheel odometry and ROS integration remain unimplemented.

At the present 3.5 m lidar maximum range, 5 m/s gives only 0.7 seconds of nominal look-ahead. Require visible free distance to exceed measured braking distance plus latency travel and a margin. Increase sensor range deliberately and validate it, or reduce allowed speed. A horizontal scan can also miss low obstacles or intersect sloped ground; test both on this elevated circuit.

After map-assisted driving works, add wheel odometry and implement camera or lidar localization fused with the installed IMU. Train or distill a second policy with only deployable observations, including realistic noise and delays. Evaluate it without privileged pose entering the policy. Ground truth may still be used by the evaluator to measure errors.

## 6. Optimize, evaluate and display the learned racing line

Run a fixed held-out suite, initially at least 100 laps per candidate across defined obstacle and friction cases. Report completion rate, collision rate, footprint boundary violations, best/median/95th-percentile successful lap time, stalls and controller interventions. A 99/100 result is evidence, not a guarantee of 99% reliability. Compare against the same baseline and seed suite. Do not select a faster policy that fails the required completion criteria.

Export successful trajectories as station, x/y/z, speed, yaw rate and boundary margin. For an empty track, fit a smooth station-indexed lateral offset and speed profile to a robust fast trajectory; replay that fitted line through the actual Unreal physics and recheck boundaries. Smoothing can create a new, invalid path. Display the validated result as a thin colored overlay above the asphalt, preserving the white edge markings. Obstacle avoidance remains reactive; one fixed line cannot serve every obstacle layout.

The next implementation milestone is the synchronized Unreal reset/step interface and a slow baseline full lap. Training should start after those work. This document describes the workflow; no RL training run or optimized lap has been completed yet.
